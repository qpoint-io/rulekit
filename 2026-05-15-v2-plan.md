# Expression Language V2 Plan

This note proposes a v2 implementation strategy for the expression language: replace the current parser with an explicit lexer/parser/AST architecture, preserve v1 behavior first, then add editor-oriented features such as bracket indexing, round-tripping, formatting, and optional source preservation.

## Current Parser Rationale

The current Ragel + goyacc implementation is a good compact evaluator-oriented parser, but it is not a good long-term fit for a hybrid freeform + GUI expression editor.

The current implementation:

- uses Ragel to recognize rich tokens such as strings, IPs, CIDRs, regexes, comments, operators, fields, and functions
- uses goyacc grammar actions to build runtime evaluator nodes directly
- skips whitespace and comments during lexing
- does not attach source spans or token ranges to expression nodes
- uses the same node types for parsing, evaluation, and compact `String()` output

That design works for parsing and evaluating rules, but it makes AST-to-expression round-tripping, localized GUI edits, trivia preservation, and source-aware diagnostics harder than they need to be.

The v2 implementation should separate these concerns:

```text
source text
  -> lossless token stream with spans/trivia
  -> explicit editable AST
  -> formatter / source rewriter
  -> evaluator or optional compiled runtime plan
```

The main goal is not just replacing goyacc with Pratt parsing. The main goal is to make the AST the stable source of truth for both freeform text and GUI editing.

## Motivation

Dot-separated field paths are convenient for common cases:

```text
request.headers.user_agent == "curl"
destination.ip in 192.168.0.0/16
```

They are less flexible when map keys contain dots, hyphens, spaces, slashes, reserved words, or other punctuation:

```text
labels["app.kubernetes.io/name"] == "api"
request.headers["user-agent"] == "curl"
payload["tls.version"] == "1.3"
```

Bracket indexing gives users an explicit escape hatch without weakening the identifier grammar.

## Proposed Syntax

Keep the existing array literal syntax:

```text
[1, "str", true]
field in [1, "str", 3]
```

Add bracket indexing as a postfix path operation:

```text
request.headers["user-agent"]
labels["app.kubernetes.io/name"]
items[0].name
```

Support root-level bracket paths for keys that cannot be written as identifiers:

```text
["top.level.key"] == 1
["weird key"] contains "value"
```

## Grammar Sketch

```text
primary       = literal | field_path | call | array | "(" expr ")"
array         = "[" [expr {"," expr}] "]"
field_path    = path_start {path_part}
path_start    = identifier | bracket_key
path_part     = "." identifier | bracket_key
bracket_key   = "[" (quoted_string | unsigned_integer) "]"
```

In a Pratt parser, `[` at the start of a primary remains an array literal. `[` after a field/path primary is parsed as postfix indexing.

## Parser Architecture

Use a Pike-style state-function lexer for tokenization, then feed those tokens into a Pratt parser for expression parsing.

```text
input string
  -> state-function lexer
  -> token stream
  -> Pratt parser
  -> AST
  -> semantic validation / compile step
  -> evaluator
```

The lexer should handle raw input concerns:

- whitespace
- `--` line comments
- `/* ... */` block comments
- quoted strings
- regex literals such as `/.../` and `|...|`
- operators and punctuation
- unquoted atoms

The Pratt parser should handle expression structure:

- operator precedence for `or`, `and`, comparisons, and prefix `not`
- grouping with parentheses
- array literals
- function and macro calls
- postfix bracket indexing

Prefer a pull-style lexer API such as `Next()` over a goroutine/channel lexer. The state-function pattern is still useful, but a pull API keeps parser control flow simple and avoids unnecessary channel overhead for short rule expressions.

## Migration Strategy

Rewrite the existing v1 feature set using the new lexer/parser/AST architecture before adding new language features.

This keeps parser architecture risk separate from language-design risk. The existing behavior should become the migration contract, and new syntax should only be added after the new implementation has strong parity with the current parser.

Suggested sequence:

1. Implement lexer parity for the current token set and accepted syntax.
2. Implement Pratt parser parity for existing expressions: literals, fields, arrays, calls, `not`, `and`, `or`, comparisons, `matches`, and `in`.
3. Build the explicit AST for the v1 grammar only.
4. Evaluate the AST directly or lower it to a current-style runtime representation.
5. Match current compact `String()` output where tests and public behavior depend on it.
6. Add parity tests that compare old and new parser behavior for parse success, compact output, eval result, missing-field behavior, and representative syntax errors.
7. Switch the existing `Parse()` API to the new parser once parity is strong.
8. Add v2 language/editor features after the replacement parser is stable.

Do not require exact yacc parse-error wording during the migration. Preserve useful line/column diagnostics and clear messages, but avoid coupling the new parser to generated-parser phrasing.

## First Milestone Non-Goals

The first milestone is a replacement parser for the v1 feature set. Keep new language and editor features out of that milestone.

Non-goals for the first milestone:

- bracket indexing
- dynamic bracket expressions
- exact whitespace/comment preservation
- compact vs multiline formatter options
- exact yacc parse-error message compatibility
- evaluator optimization or compiled runtime planning
- new natural-language negated operators such as `not in`, `not contains`, or `not matches`

It is fine for the v1 replacement parser to record source spans and token trivia early, but behaviorally visible preservation and formatting should wait until parser/evaluator parity is solid.

## AST and Round-Tripping

The AST should be designed as the shared model for both freeform text editing and a GUI expression editor. That means it should support both directions:

```text
expression -> lexer/parser -> AST
AST -> printer -> expression
```

The minimum invariant should be semantic round-tripping:

```text
Parse(Print(Parse(expr))) == Parse(expr)
```

Exact whitespace/comment preservation is a separate, stricter goal. If the editor needs to preserve comments and hand-formatted text, keep token trivia or a lightweight concrete syntax tree alongside the AST. If canonical formatting is acceptable after GUI edits, a normal AST plus a deterministic printer is enough.

AST nodes should carry:

- node kind
- source span for diagnostics and editor selection
- child nodes / operands
- normalized operator enum
- original operator spelling when useful for round-tripping or display
- literal value plus original raw token when useful

Prefer a small, explicit AST over evaluator-specific nodes. The evaluator can consume the AST directly by default. Performance-sensitive applications can add an optional second layer that compiles the AST into a runtime plan with precomputed lookups, compiled regexes, normalized operators, and other evaluation shortcuts. The editor should not have to reason about that optimized runtime representation.

## Printing and Formatting

Keep printing and formatting as explicit layers:

```text
Parse(expr) -> AST
AST.String() -> compact canonical expression
Format(AST, options) -> formatted expression
Rewrite(original, AST edits) -> preserve unchanged whitespace/comments
```

`String()` can continue to act as a compact canonical formatter for tests, logs, `EvaluatedRule`, snapshots, and debugging.

Add a formatter as an optional AST printer for editor and user-facing display:

- compact format: single-line, stable canonical expression
- multiline format: line-broken, indented expression for larger rules

The hybrid GUI/freeform editor should support three output modes:

- preserve: keep original whitespace/comments for unchanged source ranges and print only changed subtrees
- compact: canonical single-line output
- multiline: canonical formatted output with indentation

Formatting should be an explicit action or option. GUI edits should not automatically rewrite a user's whole expression unless that is the selected output mode.

For negated natural-language operators such as:

```text
field not contains "x"
domain not matches /example/
ip not in 10.0.0.0/8
```

represent them in the editable AST as a comparison with a negation flag or a distinct operator enum. A later semantic lowering step can convert them to `not (field contains "x")` if that is simpler for evaluation. This keeps GUI editing and expression printing straightforward.

## Initial Scope

Start with a deliberately small feature:

- quoted string keys for map/object access
- unsigned integer indexes for arrays/slices
- no dynamic expressions inside brackets

Do not initially support:

```text
headers[some_field]
headers[starts_with(name, "x")]
headers[1 + 2]
```

Dynamic indexing can be added later if there is a clear need, but the static form covers the main usability problem while keeping parsing, validation, and missing-field behavior straightforward.

## Semantics

In v2, dot syntax should be explicit object/path traversal. It should not fall back to matching exact keys that contain dots.

For example:

```json
{
  "data": {
    "field.name": true
  }
}
```

should be accessed as:

```text
data["field.name"]
```

and not as:

```text
data.field.name
```

Nested objects remain accessible with dot traversal:

```json
{
  "data": {
    "field": {
      "name": true
    }
  }
}
```

```text
data.field.name
```

This is a v2 behavior change from the current fallback behavior. If legacy compatibility is needed, keep it behind an explicit v1/legacy lookup mode.

Quoted bracket keys are exact map-key segments:

```text
obj["1"]
```

means the string key `"1"`, while:

```text
obj[1]
```

means numeric index `1` into an array or slice.

Existing dot-path behavior should remain compatible. If current lookup supports both flat keys like `"destination.ip"` and nested maps like `destination: {ip: ...}`, bracket indexing should act as the explicit form for exact path segments:

```text
destination.ip
destination["ip"]
["destination.ip"]
```

The last form should refer to the exact top-level key `"destination.ip"`.

## Input Normalization

Skip schema support initially. Keep input dynamic and easy to provide.

Support two portable JSON-oriented input styles:

- plain JSON key/value documents
- fully typed JSON values

Plain JSON may optionally enable annotated key suffixes for convenient type hints:

```json
{
  "name": "hello",
  "src.$ip": "1.2.3.4",
  "dst.$cidr": "10.0.0.0/8",
  "payload.$bytes_hex": "474554",
  "max.$uint64": "18446744073709551615"
}
```

When annotated-key decoding is enabled, the annotation suffix is input metadata and is not part of the field path. For example, `src.$ip` normalizes to field `src` with Rulekit type `ip`.

Potential initial suffixes:

- `.$ip`
- `.$cidr`
- `.$mac`
- `.$bytes_hex`
- `.$bytes_base64`
- `.$int64`
- `.$uint64`
- `.$float64`

Annotated-key decoding must be opt-in because JSON object keys can contain arbitrary strings. If a caller needs an exact key that collides with an annotation suffix, they can disable annotated-key decoding or use fully typed JSON.

Fully typed JSON is the collision-free exact mode:

```json
{
  "src": { "$type": "ip", "value": "1.2.3.4" },
  "payload": { "$type": "bytes", "encoding": "hex", "value": "474554" },
  "u64": { "$type": "uint64", "value": "18446744073709551615" }
}
```

The evaluator should consume a normalized Rulekit value model rather than host-language-specific values. Host-specific inputs such as Go `KV`, plain JSON, annotated-key JSON, TypeScript values, and Rust values should be adapters into that model.

## Reliability Notes

- Keep tokenization and semantic validation separate.
- Preserve source spans for useful syntax errors.
- Reject malformed brackets early: missing closing bracket, empty key, unsupported index expression.
- Add parser tests that distinguish array literals from postfix indexing.
- Add evaluation tests for flat keys, nested maps, string keys with dots, and numeric indexes.

## Go-Only Implementation Phases

The immediate roadmap should stay focused on the Go implementation before adding other host-language adapters or editor integrations.

### Phase 1: Parser Replacement and V2 Path Semantics

Status: complete.

Scope:

- replace Ragel/goyacc with the hand-written lexer and Pratt parser
- preserve the root `Parse()` API and current evaluator behavior where v2 semantics do not intentionally differ
- add bracket path indexing for quoted keys and unsigned numeric indexes
- add root bracket paths such as `["destination.ip"]`
- change dot paths to explicit nested traversal with no flat dotted-key fallback
- add opt-in JSON input normalization for annotated keys and fully typed values
- keep dynamic bracket expressions out of scope

### Phase 2: Real AST Boundary

Add an internal AST boundary while keeping public `Parse()` returning `Rule`.

Scope:

- define explicit AST node types for binary expressions, unary expressions, literals, paths, arrays, and calls
- include normalized operator enum, raw operator spelling, and source spans
- make the parser produce AST first
- add lowering from AST to the current evaluator `Rule` nodes
- keep existing `String()` behavior unchanged through the current evaluator nodes

This gives the Go implementation an editor/compiler architecture without another runtime behavior change.

### Phase 3: Canonical AST Printer

Add semantic round-tripping from AST.

Scope:

- implement compact canonical AST printing
- add invariant tests for `Parse(Print(Parse(expr))) == Parse(expr)`
- start moving root string expectations toward the AST printer where safe
- preserve current evaluated-rule formatting unless intentionally changed

### Phase 4: Public Go AST API

Expose AST deliberately for Go callers.

Scope:

- add a public `ParseAST`-style API
- add a `Compile` API that lowers AST to `Rule`
- keep `Parse(expr)` as `Compile(ParseAST(expr))`
- document AST mutability and editing expectations

This lets Go tools build GUI/freeform editors without depending on evaluator internals.

### Phase 5: Formatter

Add explicit formatting modes.

Scope:

- add `Format` with compact and multiline modes
- support indentation options
- add deterministic formatting tests
- do not preserve exact original whitespace or comments yet

Canonical formatting should land before source preservation because it is simpler and gives changed subtrees a stable printer.

### Phase 6: Trivia-Aware Tokens

Keep comments and whitespace in the token stream.

Scope:

- have the lexer emit or store leading/trailing trivia
- have AST nodes carry token spans/ranges
- keep parser semantics trivia-insensitive
- use node spans for better diagnostics where possible

This is the foundation for source-aware editing and later preservation.

### Phase 7: Source-Preserving Rewrite

Preserve unchanged source while printing edited subtrees.

Scope:

- represent edits against AST nodes
- reuse original text for unchanged source ranges
- print only changed subtrees
- preserve comments and whitespace around unchanged regions

This is the editor-grade round-trip layer and should come after AST and formatter stability.

### Phase 8: Optional Runtime Compile Plan (Removed)

Optimize evaluation without changing the AST contract.

Scope:

- compile AST to an optimized runtime plan
- precompute path lookups, regexes, normalized operators, and other stable evaluation details
- keep current evaluator behavior as the semantic contract
- add benchmarks before and after optimizer work

This phase was removed from v2 because the temporary `Plan` wrapper did not provide a distinct runtime representation; it only delegated to `Rule`. Future optimizer work should add a real evaluator representation only when profiles justify it.

## Follow-Up V2 Design Phases

The first eight phases establish the parser, AST, printer, formatter, rewrite, and initial compile-plan boundaries. The next phases should refine the public v2 API around explanation, input, printing, functions, and performance. Backward compatibility with the current v1-style API is not a design constraint for these phases.

### Phase 9: Rule Print API

Replace loose formatter options with a typed print API.

Scope:

- make `String()` return compact canonical output
- add `Print(mode)` with typed modes rather than a broad options bag
- support exact original source through a source print mode
- support compact canonical output through a compact print mode
- support multiline canonical output through a multiline print mode with indentation attached only to multiline mode
- keep source-preserving rewrite as a separate operation, not as `String()` behavior

Sketch:

```go
type PrintMode interface{ printMode() }

func Source() PrintMode
func Compact() PrintMode
func Multiline(indent string) PrintMode

type Rule interface {
    String() string // compact canonical
    Print(PrintMode) string
}
```

`Print` should not return an error for parser-produced rules. Invalid manually constructed ASTs can be handled by construction-time validation instead of print-time errors.

### Phase 10: Trace-Based Evaluation Explanation

Replace `EvaluatedRule` as the primary explanation mechanism with an explicit trace tree.

Scope:

- keep short-circuit visibility as the primary goal
- attach evaluated values and errors to AST/evaluation branches
- mark branches as active, pruned, passed, failed, or missing
- make trace output suitable for GUI visualization
- treat progressive residual-rule evaluation as out of scope unless a concrete need returns
- stop using runtime evaluator-node rewriting as the explanation model

Sketch:

```go
type Trace struct {
    Node     ASTNode
    Value    any
    Error    error
    Active   bool
    Pruned   bool
    Children []*Trace
}

type Result struct {
    Value         any
    Error         error
    MissingFields []string
    Trace         *Trace
}
```

The old `EvaluatedRule` behavior was useful for v1, but v2 should favor explicit explanation data over serialized evaluator-node fragments.

### Phase 11: Context-Aware Input API

Rename the evaluation data model around a single `Input` abstraction and make eval context-aware.

Scope:

- replace `Ctx` as the primary eval argument with `Input`
- make eval accept `context.Context`
- keep trace/functions/macros in explicit eval options rather than in `Input`
- avoid a design with both `KV` and `Resolver` fields competing as parallel input sources
- allow `KV` to be adapted into `Input`
- allow lazy leaf values inside `KV`
- allow nested `Input` values inside `KV` so a subtree can take over path resolution
- allow custom path-based `Input` implementations for callers that want to avoid building nested objects

Sketch:

```go
type Input interface {
    Get(context.Context, []PathSegment) (any, bool, error)
}

func FromKV(KV) Input
func FromFunc(func([]PathSegment) (any, bool, error)) Input
func FromContextFunc(func(context.Context, []PathSegment) (any, bool, error)) Input

type LazyValue func() (any, error)
type LazyContextValue func(context.Context) (any, error)

type Opts struct {
    Trace     bool
    Functions map[string]*Function
    Macros    MacroSet
}

type Rule interface {
    Eval(context.Context, Input, Opts) Result
}
```

Resolution policy for `FromKV`:

- traverse explicit path segments
- if a resolved value is `LazyValue`, call it and memoize it for that eval/input instance
- if a resolved value is `LazyContextValue`, call it with the eval context and memoize it
- if a resolved value implements `Input`, delegate the remaining path segments to it
- populate `Result.MissingFields` only after the active input source cannot resolve the path

This supports both simple Go `KV` use and expensive lazy materialization for large per-request input contexts.

### Phase 12: Macro Contract

Define macros as zero-argument inline expansion of named rule expressions.

Scope:

- macros are reusable rule-language snippets, not Go code
- macros are serializable as source/AST
- macros remain zero-argument unless a strong need for parameterized macros appears
- functions remain the mechanism for runtime Go behavior
- GUI/editor tooling should be able to show macro source, docs, and expanded trace context

Sketch:

```go
type Macro struct {
    Name   string
    Source string
    AST    *AST
    Rule   Rule
    Doc    string
}
```

Macro expansion should preserve clear trace information so users can see both the macro call and the expression that made it pass or fail.

### Phase 13: Function API Overhaul

Redesign functions around explicit schemas and ergonomic Go registration.

Scope:

- keep function arguments positional in expression syntax
- name positional arguments for UX, docs, validation, and editor forms
- make return type optional initially, but supported for editor validation and docs
- rename call argument access to `FunctionArgs`
- support both named and indexed argument access
- add reflection-based registration helpers for one-time setup ergonomics
- keep a manual non-reflective registration path for callers that want full control

Sketch:

```go
type Function struct {
    Args   []ArgSpec
    Return Type
    Doc    string
    Eval   func(context.Context, FunctionArgs) (any, error)
}

type FunctionArgs struct {
    // implementation-owned positional values and name indexes
}

func (a FunctionArgs) Index[T any](int) (T, error)
func (a FunctionArgs) Named[T any](string) (T, error)

func Func(name string, args []ArgSpec, impl any) Function
```

The reflection-based `Func` builder may inspect the implementation signature once at registration time. Runtime eval should still use the compiled schema and avoid reflection in hot paths where possible.

### Phase 14: Eval Performance Hardening

Optimize hot-path eval after the new input and trace APIs are shaped.

Scope:

- keep reflection out of runtime eval paths
- compile paths once and avoid per-eval path parsing or splitting
- avoid debug `defer` costs when debug output is disabled
- benchmark happy-path eval, missing-field eval, path lookup, lazy input, and trace-enabled eval separately
- optimize trace collection so callers can choose whether to pay for it
- keep missing-field allocation improvements medium priority unless profiles show real production impact

Known findings:

- per-eval `strings.Split` in top-level field lookup caused avoidable allocation and slowdown
- unconditional debug `defer` closures in comparison functions were a major happy-path cost
- missing-field paths allocate sets and path strings, but this is acceptable unless missing-field eval is hot
- source/editor features should not impose cost on eval when trace/source preservation is not requested
